VTA Auth Demo

A static-file harness for exercising the VTA's auth surface from a browser.

1. Connect

Must be reachable from this page. The VTA must include this page's origin in [server] cors_origins — see the README.

2. Bootstrap auth (paste JWT)

First-time setup: get a JWT from pnm auth show-token, paste it here. Unlocks Step 3 (enrol passkey) and Step 5 (sessions + trust-tasks) without going through passkey login.

3. Enrol a passkey VM

Adds a WebAuthn passkey as a verificationMethod on a WebVH-managed DID. Requires an admin JWT (from Step 2). The browser drives navigator.credentials.create; the VTA publishes the new VM via a WebVH LogEntry.


  


  

    
4. Passkey login

    
Once a DID has a passkey VM (from Step 3 or already enrolled), use it to obtain a JWT directly — no DIDComm round-trip.

7. DIDComm primitives (vti-didcomm-js)

    
Smoke-test for the browser-side DIDComm v2 stack — resolves a DID, generates an ephemeral sender key, and packs an authcrypt JWE. No VTA round-trip; the JWE is just shown, not delivered. Works with did:key:z… (offline) and did:webvh:… (fetches the log over HTTPS).

    
    
    

      
      
    

    

  


  

    
8. DIDComm auth — POST /auth/ (vti-didcomm-js)

    
Drives the full legacy auth flow that previously required pnm auth: requests a challenge, authcrypt-packs a DIDComm response to the VTA's keyAgreement key, POSTs it to /auth/, and stores the returned JWT. The ephemeral client DID must already be in the VTA's ACL (the demo prints it so you can run pnm acl create --did <that> --role admin first). Successful auth populates Step 5/6 just like passkey login.

    
    

      
      
      
    

    

  


  

    
9. DIDComm via mediator (vti-didcomm-js)

    
The VTA-not-reachable path: instead of POSTing to the VTA's REST API, this routes a DIDComm message browser → mediator → VTA → mediator → browser over a live WebSocket. It authenticates to the mediator (subprotocol-bearer WS), enables message-pickup 3.0 live delivery, sends a trust-ping wrapped in routing/2.0/forward addressed to the VTA, and awaits the thid-correlated ping-response. Reuses the ephemeral client DID from Step 8. Trust-ping needs no VTA ACL — only that the mediator lets the client connect.
