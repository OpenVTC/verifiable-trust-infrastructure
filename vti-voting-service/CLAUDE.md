## What this crate is

(The crate's full entry from the workspace `CLAUDE.md` crate map.)

**The voting service** (`publish = false`): a host service holding ballot boxes for any number of communities, never a roster. Its identity is a `did:webvh` its operator's VTA mints from the `ballot-box` template (`vti-voting-service setup`, two-phase like the witness; keys in `[secrets]`). Communities and auditors reach it over **TSP, then DIDComm** through its own mediator session (`vti_common::host_session`; the transport-proven sender must be the document's issuer). **HTTPS** (`POST /trust-tasks`, advertised `TrustTaskHTTPS`) stays only as the sessionless cast door VTI-VOT-004 requires: a one-time key has no mediator session to take a receipt on, and opening one would hand the mediator the voter's address and timing. One dispatcher (`dispatch::answer`) behind both, running every document through `vti_trust_task_server::Spine` (#2576): each task's proof / recipient / `issuedAt` requirement comes from its pinned specification (`vti_specs::schema_index::spec_policy_for`), never a list here; the routing table (`dispatch::SERVED`) names each served version by its generated payload type, held equal to the pinned `voting/*` set by a test; the service's own rules are pieces handed to the pipeline — `Gate` (issuer = transport sender, served type, a cast signed by a `did:key`, VTI-VOT-003), `Verifier` (which DIDs are resolved on which binding, a verification deadline answered `unavailable`), `freshness_for` (the VTI-OPS-024 window for a community's or trustee's request; none for a cast, which may be resent until voting closes, VTI-VOT-004, nor for a read). The duplicate-id record (VTI-OPS-025 … 029) is `StoreAcceptedIds` in `<data_dir>/store` (`accepted_ids`): a redelivered document is answered with its first answer (a cast's receipt included), a replayed read with `204`; a resend of the same cast in a new document still reaches the ballot box, which answers `alreadyCounted`. Refusal statuses are the HTTPS binding's table (`proofInvalid`, `expired`, `unsupportedVersion` are 422). Every answer signed as its DID (receipts and heads are evidence), and one that cannot be signed is not sent; a file journal (`sync_data` before answering). Without `[identity]` it runs as a test `did:key` over HTTPS only
