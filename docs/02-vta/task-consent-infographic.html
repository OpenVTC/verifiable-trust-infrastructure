◆ Verifiable Trust Agent · Approvals

DTTE: consent bound to the act, not the session

Delegated Trust-Task Execution is how a VTA requires that a different party agrees to this exact operation before it runs. Not a login, not a 15-minute elevation — an approval bound to one payload, re-checked against the world at the moment it is used, and consumed once.

Payload-bound digest, not session N-of-M with requester exclusion Re-verified at consume Signed effects shown to the human Runtime-managed via pnm approvals

What changed

One model replaced three

A VTA used to answer "does this need another human?" in three unreconciled places. An operator could be refused for a reason nothing they could read explained. That collapsed into a single rule list — and DTTE is the mechanism the consent half of it drives.

Retired

Delegated step-up

A third party ratified, and the result was a session elevation: approve one ACL grant, and for the next fifteen minutes every gated operation passed.

  • Bound to a session, not an act
  • Keyed on 11 fixed op-class slugs
  • Config file + restart; no runtime surface
  • No threshold, no requester exclusion
  • Approver saw no computed effects
Live today

Task consent (DTTE)

The approval authorizes exactly the act described. Approving one thing authorizes one thing — there is no window in which other operations pass.

  • Bound to the payload digest
  • Keyed on the task type URI itself
  • pnm approvals at runtime, no restart
  • N-of-M, optionally excluding the requester
  • Approver reads VTA-signed effects
Note.

Everything the earlier step-up vision listed as next — M-of-N quorum on one challenge, four-eyes on the most dangerous actions — ships today under DTTE, with strictly tighter binding. Delegated step-up was removed rather than ported because consent does the same job better.

The reasoning

Why it is shaped this way

Three properties do the real work. Each answers a specific way approvals go wrong.

01 — BINDING

Approve an act, not a window

The digest covers the task URI and its canonical payload, length-prefixed so the boundary cannot shift. An approver cannot be shown one payload while a different one executes, nor approve a benign URI whose payload canonicalizes like a destructive one's.

02 — FRESHNESS

The world is re-checked at consume

A grant minted minutes ago is not trusted blindly. Policy, approver enrolment, and the pinned state are all re-asserted before the handler runs. An approver removed from the set during the window invalidates the grant.

03 — SEPARATION

An approver needs no power to act

Set membership is sufficient to answer — no ACL entry required. The device that agrees to a key revocation holds no authority to revoke keys itself, which is exactly the posture you want for an approver.

End-to-end

The ceremony

Three Trust Task URIs, of which exactly one is dispatched. There are no DTTE-specific REST endpoints — the gate runs on both transports, but the ceremony itself is Trust-Task-only.

1
● Requester → VTA

Submit the task; the gate refuses it

The PDP returns requireConsent. The VTA computes the executor-internal payload digest, parks the request as a pending record, and refuses — handing back everything needed to answer: challenge, digest, approver set, threshold, and whether the requester may self-approve.

auth:consent_required · VtaError::ConsentRequired
2
● VTA → Approver devices

Push a signed question carrying the effects

The VTA dry-runs the handler it is about to invoke, signs the resulting effects and a state pin into the request, and pushes it to each set member. The effect kind set is open — a surface must render a kind it does not recognise.

task-consent/request/0.1 · outbound only, no handler
3
● Human

Compare the match code, read the effects

Six hex characters, derived from the decoded digest bytes — never from the multibase string, whose first three characters are the constant zQm. Slicing the encoded form would leave ~17.6 bits where the operator believes they are comparing ~35, while still looking like six random characters.

match code = hex(digest)[..6] · UI-only, no wire field
4
● Approver → VTA

Sign a decision echoing the challenge

A Data-Integrity proof authorizes the document — the VTA does not read the sender's ACL claims at all. Set membership is checked, the threshold counted, and the requester barred if the rule says so. This is the only dispatched URI of the three.

task-consent/decision/0.1 · DI-signed
5
● VTA

Mint a single-use grant, notify the requester

Threshold met inside the window → a grant keyed to the digest and the requesting DID. Every step is audited: consent.required → consent.decision → consent.granted → consent.consumed.

task-consent/granted/0.1 · fire-and-forget notice
6
● Requester → VTA

Re-submit; the grant is consumed and re-checked

The identical task goes back in. The grant is consumed before the checks can refuse it — single-use is single-use even when the outcome is a refusal. Policy, approver enrolment and the state pin are all re-asserted; only then does the handler run.

executed · or auth:consent_stale

The surface

What you can drive, and what you cannot

Honest state of the surface as it stands. Amber is a real gap, not a roadmap aspiration.

Declaring the rule

  • LIVE pnm approvals require at runtime, no restart
  • LIVE N-of-M threshold + requester exclusion
  • LIVE Context-scoped rules; scoped beats unscoped
  • LIVE Refused at write time if unsatisfiable
  • LIVE explain names why a rule can never be met
  • GAP Trust-Task transport only — REST returns 404

Answering the question

  • LIVE DI-signed decision from a mobile approver
  • LIVE Set membership alone suffices — no ACL entry
  • LIVE CLI waits on the gate instead of dying
  • LIVE Stops polling the instant a denial lands
  • GAP No Rust client can sign a decision
  • GAP No read-only "approved yet?" status task

Operating it

  • LIVE Full audit chain on every ceremony step
  • LIVE Offline break-glass for a rules lockout
  • LIVE Seed-once config for IaC bring-up
  • GAP enforcement needs a config edit + restart
  • GAP list/explain do not show enforcement state
  • GAP vta setup --from cannot carry [policy]

How to use it

From nothing to a gated task

Four steps. Only the first needs a restart.

STEP 01

Turn the PDP on

Rules are stored and listed but nothing consults them while enforcement is off — and it defaults off. There is no runtime surface for this flag. 

# config.toml — then restart
[policy]
enforcement = true
STEP 02

Declare the rule

Keyed on the task type URI. Your client must be on DIDComm or TSP transport — the REST arm is unimplemented. 

pnm approvals approvers add ops did:key:z6Mkngm…
pnm approvals approvers add ops did:key:z6MkSecond…

pnm approvals require \
  …/spec/vta/webvh/dids/update/1.0 \
  --consent --set ops --min 2 --exclude-requester
STEP 03

Verify it can be satisfied

explain tells you when a rule can never be met, rather than letting you find out at the next request. 

pnm approvals explain …/dids/update/1.0

  requires: consent — 2 approval(s) from `ops`,
            requester excluded
  approvers: 1 member(s) — fewer than the 2
            required, so this task can never run
STEP 04

Run the gated task

The CLI submits, prints the match code, and waits. Approve on a device; the re-submit goes through. Timing out is safe — the pending survives. 

pnm did-mgmt dids edit …

# waiting for approval · match code 3b0c7f
# approve on an enrolled device
Upgrading?

A config still carrying [[policy.require_consent]] or [auth.step_up] will not start — deliberately, and the error names the fix. Your previous consent rules are also deleted rather than orphaned: the first boot after upgrade removes the config:require-consent row, because the old block was reconciled from file every boot and leaving it would strand a rule nothing could read back or remove. Re-declare with pnm approvals require.

Interop hazard.

The digest moved from bare hex to digestMultibase in trust-tasks 0.4. Any approver stack computing a digest independently — the browser plugin, anything on an older vta-mobile-core — must move in lockstep. A mismatched pair produces an approval that is given, accepted by the human, and then silently never takes effect.

The one-sentence version

Consent is the strong form

Task consent authorizes an act; re-authentication authorizes a session. Reach for --consent whenever the point is that a different party agrees — it binds to the payload digest, re-asserts the world at execution, supports N-of-M with requester exclusion, and puts a VTA-signed statement of what the task will actually do in front of the human. Reach for --reauth only when you mean "prove it is still you at the keyboard", which raises the assurance of the caller's own session and nothing more.
