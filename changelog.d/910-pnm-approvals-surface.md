### vta-config 0.3.1 / vta-sdk 0.21.9 / vta-policy 0.1.4 / vta-service 0.14.18 / vta-cli-common 0.10.26 / pnm-cli 0.11.20 — `pnm approvals`: approval requirements manageable at runtime (#910)

Second slice of the approvals convergence, and the operator-facing one. Additive
throughout: nothing is retired here and no path is un-gated, so it can land
ahead of the trigger collapse.

- **`pnm approvals {list,require,remove,approvers,explain}`** — the declarative
  rules and their approver sets, edited live over whatever transport the VTA
  advertises. Each command is a read-modify-write of the reserved policy row
  through `policy/{get,upsert}`, carrying `expectedVersion` so two operators
  editing at once collide instead of silently overwriting each other.
  `explain <task-uri>` answers the question that started this: what does this
  task require, who can satisfy it, and — if the answer is "nobody" — it says so
  outright rather than leaving the operator to discover it at the next request.
- **The Rego is generated by the CLI**, then re-derived and byte-compared by the
  VTA. There is deliberately no `--module` escape hatch on this surface: a
  declarative row whose Rego disagreed with its rules would make everything
  `approvals list` prints advisory rather than true. Hand-authored Rego belongs
  to `pnm policy upsert`.
- **`[policy.approvals]` / `[policy.approver_sets]` are a seed, applied once**
  when the VTA boots without a declarative row — the bring-up path for a fresh
  or IaC-provisioned VTA. Deliberately **not** the reconcile-every-boot
  behaviour of the consent policy it supersedes: once rules are editable at
  runtime, re-reading the file every boot means a restart weeks later silently
  reverts an operator's change. A security control that quietly undoes itself is
  worse than one that is awkward to change. Pinned by a test.
- The consent gate now resolves approver sets from the declarative row first,
  falling back to config — so `pnm approvals approvers add` takes effect without
  a restart, while a VTA whose sets are still in config keeps working.
- The declarative row sits at priority 200, above the legacy config-synthesized
  consent row (100). A task named by both would otherwise tie, and ties break by
  keyspace iteration order — which requirement applied would have depended on
  disk layout.
- Write-time refusals cover the failure that prompted this work: an unsatisfiable
  rule (undefined or empty approver set, a threshold larger than its set) is
  refused when written, and an unsatisfiable *seed* stops the VTA at boot rather
  than at the first request it blocks.
